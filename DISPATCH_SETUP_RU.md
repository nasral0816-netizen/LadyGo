# LadyGo — архитектура и эксплуатация диспетчеризации

## Текущая схема

Live backend использует DB triggers, защищённые RPC, Realtime, клиентский fallback polling и два cron задания. Отдельная Edge Function dispatch-loop не развёрнута и не нужна текущей схеме. Не добавлять LADYGO_DISPATCH_SECRET или дополнительный loop без отдельного решения.

## Поток заказа

1. Пассажир получает серверную цену через pricing-service и отправляет create_order с ID quote и координатами.
2. pricing-service v7 проверяет JWT, что пользователь — пассажир, quote принадлежит ему, не истёк и не использован; проверяет адреса и координаты.
3. Заказ вставляется через пользовательский Supabase client. DB trigger выполняет проверку quote и запускает ladygo_dispatch_next_driver.
4. Кандидат должен иметь роль driver, approved driver application и driver profile, свежую online presence и GPS; исключаются занятые водители и водители с незакрытым оффером.
5. Создаётся персональный order_offers со сроком действия 25 секунд.
6. Водитель видит собственный оффер через RLS/Realtime и принимает его через ladygo_accept_order.
7. RPC блокирует строку заказа FOR UPDATE, проверяет статус заказа и действующий персональный оффер, затем назначает водителя. Второй параллельный accept должен быть отклонён.
8. Отказ/истечение позволяет подобрать следующего водителя. Клиентский fallback повторяет dispatch RPC раз в 12 секунд, пока заказ активен и не назначен.
9. Heartbeat записывает свежую GPS-координату до обновления driver_presence; presence trigger после этого может запускать dispatch для ожидающих заказов.
10. Статусы поездки контролируются серверной state machine. GPS точки записываются защищённым RPC с проверкой участника, статуса и допустимой скорости.
11. Контакты раскрываются только участникам активной поездки при действующем contact lease. Завершение/отмена закрывает доступ по проверке статуса.
12. Push — дополнительный канал, не источник истины. Realtime/БД определяют состояние заказа.

## Cron

Live cron:
- ladygo-expire-stale-offers — каждую минуту.
- ladygo-dispatch-scheduled-orders — каждую минуту.

Cron выполняет обработку просроченных предложений и запланированных поездок. Не утверждать, что он запускает отдельную dispatch-loop Edge Function.

## Edge Functions и секреты

- pricing-service: версия 7, verify_jwt=true; использует Supabase стандартные серверные переменные, проверяет JWT и использует service-role key только внутри функции.
- send-driver-offer-push: версия 5, verify_jwt=false для webhook. Проверяет заголовок через Vault-backed RPC ladygo_verify_push_webhook_secret; ключ service role только серверный.
- Отдельный LADYGO_PRICING_SECRET и LADYGO_DISPATCH_SECRET текущей реализации не требуются.
- Не записывать секреты в клиент, Git, APK, логи или документацию.

## Проверки безопасности

- Только проверенные водители могут становиться online и принимать персональные офферы.
- ladygo_accept_order сериализует принятие блокировкой заказа.
- Отдельная миграция сохраняет GPS до переключения online.
- Миграция admin cap сериализует назначения обычных администраторов, ограничивая их 15.
- Миграция quote-route binding сохраняет координаты pickup/destination в price_quotes и сверяет их с координатами заказа.
- RLS включён на orders/offers/locations/presence/trip_tracks/profiles/push/support tables.
- Контакты и треки ограничены участниками активной поездки.
- Проверка на чужие данные под независимыми JWT и реальная двойная гонка accept ещё должны быть выполнены на staging.

## Что подтверждено / не подтверждено

Подтверждено по live БД/конфигурации: Edge Functions pricing-service v7 и send-driver-offer-push v5 активны; cron jobs активны; миграция GPS-before-online и миграция сериализации лимита администраторов применены; RLS включён на ключевых таблицах.

Не подтверждено: пассажирский заказ с действующим JWT, онлайн heartbeat с физического Android, доставка push на устройство, водительский accept, GPS в движении, завершение и рейтинг. Сейчас 0 онлайн-водителей и 0 push-токенов. Один существующий активный заказ не трогать.

## Чек-лист реального E2E

1. Установить проверенный APK на отдельное устройство пассажира и устройство одобренного водителя.
2. Войти под двумя отдельными тестовыми аккаунтами; водителю разрешить location и notifications.
3. Убедиться, что push token записался в driver_push_tokens и user_push_tokens; проверить heartbeat и свежую строку driver_locations.
4. Создать новый тестовый заказ пассажиром; проверить orders, trigger, order_offers, Realtime и Expo ticket.
5. Принять оффер водителем; убедиться, что второй водитель не может принять тот же заказ.
6. Проверить arrived → in_progress → completed, GPS samples, расчёт финальной цены, рейтинг и историю.
7. Отдельно проверить пассажирскую/водительскую отмену, истечение/отказ оффера, потерю сети и восстановление.
8. Проверить отсутствие доступа чужих аккаунтов к заказам, контактам, трекам и токенам.

До этих тестов нельзя заявлять, что реальные поездки или push delivery уже работают.
