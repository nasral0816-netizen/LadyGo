# LadyGo — технический аудит и план завершения

Проверка исходников GitHub на 2026-11-23. Это аудит репозитория, а не подтверждение состояния удалённого Supabase-проекта: прямого подключения к Supabase SQL/API в текущем рабочем сеансе нет.

## Подтверждено в коде

- Expo SDK 55, React Native 0.83.10, Supabase JS v2.
- Supabase Auth: регистрация/вход, восстановление локальной сессии через AsyncStorage и `onAuthStateChange`.
- Профиль читается из `profiles`; роль управляет доступными экранами.
- Форма водительской анкеты и загрузка фото в Storage.
- Админский UI для проверки водительских заявок, истории заказов, поддержки и управления администраторами.
- Поддержка: создание и просмотр обращений, ответ администратора.
- Заказы пассажира хранятся в `orders`; отдельная история тестовых записей использует `demo_orders`.
- В репозитории есть SQL для онлайн-присутствия водителя, GPS, коротких персональных предложений, атомарного принятия заказа, статусов поездки и realtime.
- Push Edge Function `send-driver-offer-push` и регистрация Expo push-токенов водителя присутствуют.
- Android workflow собирает release APK через Gradle.

## Изменения этой ветки

1. Регистрация Expo push token теперь выполняется для любого вошедшего пользователя в `user_push_tokens`; водители дополнительно регистрируются в `driver_push_tokens`. Добавлены Android-каналы для заказов и обновлений поездки.
2. Устаревшая цена сбрасывается при запросе нового тарифа. Создание заказа больше не использует локальную приблизительную цену как подтверждённую: требуется ответ тарификации с `price_token` и положительной суммой.
3. Кнопка заказа заблокирована до получения серверного quote.
4. Вызов принятия заказа больше не передаёт цену, выбранную клиентом-водителем.
5. Новая миграция переводит bucket `ladygo-driver-media` в private и разрешает чтение только владельцу, администратору и пассажиру активной поездки (только фактически привязанных фото назначенного водителя). Миграция также запрещает водителю переопределять сохранённую цену через аргумент RPC.

## Критические блокеры перед реальным запуском

### Тарификация и создание заказа
- В дереве репозитория отсутствует исходник Edge Function `pricing-service`, хотя клиент вызывает её для получения quote.
- Текущий клиент создаёт запись прямым INSERT в `orders`; полученный `price_token` не передаётся серверу для проверки и не подтверждается отдельной серверной функцией создания заказа.
- Новая защита не позволяет водителю изменить цену при принятии, но сама по себе не доказывает, что `estimated_price_rub` был рассчитан сервером. Нужна серверная проверка подписанного quote при создании заказа.
- До появления и проверки этой серверной цепочки нельзя считать цену защищённой от подмены и нельзя объявлять коммерческую диспетчеризацию готовой.

### Схема и RLS Supabase
- `schema.sql` — устаревший минимальный bootstrap для `profiles` и `orders`, а не полная схема текущего приложения.
- В миграциях есть ссылки на таблицы/функции, полное создание которых в репозитории не обнаружено (в частности, `driver_applications`, `notifications`, `city_tariff_configs`, `driver_rating_stats`, `ladygo_list_admins`, `ladygo_set_admin_by_email`). Они могут существовать в удалённой БД, но без доступа к ней это не подтверждено.
- Применение всех миграций на чистом проекте по одному только текущему репозиторию не подтверждено.
- Storage bucket ранее создавался как публичный. Ветка добавляет исправляющую миграцию, но пока она не применена, объекты могут оставаться публичными.
- Нужно проверить реальные политики всех таблиц, Storage, Realtime, grants и SECURITY DEFINER RPC на удалённой базе.

### Роли и администрирование
- UI ожидает `profiles.is_super_admin` и RPC `ladygo_list_admins` / `ladygo_set_admin_by_email`.
- В текущем наборе миграций не обнаружены полные определения этих RPC, ограничения до 15 обычных администраторов и журнал аудита действий администраторов. Это необходимо подтвердить/добавить после получения фактической схемы, не создавая дубли.
- Проверка роли в интерфейсе не является границей безопасности; все операции должны быть защищены RLS/RPC на сервере.

### Остальные функции
- В этой ветке восстановлен realtime-чат пассажира и водителя на `trip_messages`; требуется подтвердить, что таблица, RLS и Realtime publication реально применены в рабочей БД.
- Экран входа не содержит полноценного восстановления пароля. Телефонный вход использует синтетический email; в клиентском исходнике есть жёстко прописанные соответствия телефонов и email. Нужна безопасная миграция телефонной авторизации, прежде чем удалять эти соответствия, чтобы не потерять доступ существующим аккаунтам.
- В публичном репозитории присутствует файл `.env`. Его содержимое не открывалось. Проверь его в истории Git и отзови/замени любые действующие ключи, которые могли попасть в коммиты. Не помещай service_role key в приложение или публичные файлы.
- Сетевые ошибки частично переводятся в понятные сообщения, но полноценный offline/retry/outbox сценарий не реализован.
- Для Android background location нужны проверка на реальном устройстве, разрешение «Всегда», foreground service и проверка поведения после перезапуска/выгрузки приложения.
- API-ключ карты в app config должен иметь ограничения по Android package/signing certificate и разрешённым API.

7. Провести сценарий на двух Android-устройствах с отдельными пассажирским и водительским аккаунтами.

## Условия приёмки реального заказа

Пассажир создаёт заказ с действительным серверным quote; запись появляется в `orders`; только один подходящий онлайн-водитель получает активное предложение; другой водитель не может принять его; при истечении/отказе сервер предлагает заказ следующему; после принятия пассажир видит назначенного водителя и его свежую геопозицию; статусы переходят по серверной state machine; отмена и завершение освобождают водителя; история синхронизируется между устройствами.
